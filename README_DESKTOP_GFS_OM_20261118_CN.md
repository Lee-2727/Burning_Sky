# Burning Sky V2.2.0 · GFS / OM 桌面复现版

这个 ZIP 是从用户的 **V2_2_0.zip** 展开后直接增量增加桌面诊断功能，不是从旧版重做。`burning_sky/` 原有严格球面光路和 2026-11-18 GFS 云量冲突保护没有被回滚。网页的尚未描述的 BUG **未在本包中声称修复**。

## 最快的使用方法（Windows）

1. 解压完整 ZIP，保持文件夹结构。首次安装依赖双击 `INSTALL_DESKTOP_DEBUG_DEPENDENCIES.bat`（建议 Python 3.11 或 3.12）。
2. 双击 **`START_GFS_OM_DESKTOP_DEBUG.bat`**。**不要点旧的 `启动桌面版.bat`**：它仍然启动普通的非诊断版。
3. 窗口顶部默认勾选「开启 OM 二维云场 + API 垂直剖面融合」。直接在线查询时会使用共享 Engine 的最新原生云量保护，API 遇 429 时应停止请求并按原有逻辑处理。不要为了复现反复联网请求。
4. 点击 **「导入案例 ZIP 并离线核对云量」**，可以选择以前保存的 `2026年11月20日_合肥_GFS.zip`（或其他 Burning Sky 案例 ZIP）。直接显示 `距离 | 云层 | 原生 API | 原 OM | 旧值 | 当前应使用值 | 差值`，**完全离线**，无需解压旧案例，也不会修改旧 ZIP。
5. 对照表可导出 CSV、JSON；超出 25 个百分点的差异会标出浅色底。旧案例没保存 `pressure_layer_proxy` 来源标签时，只有明确为 GFS 且已经保存 OM 水平云场的点，才按 GFS 压强层 proxy 恢复来源标签；EC 不动。
6. 想在原桌面 UI 展示案例或尝试离线全链路重算，可在对照窗口按 **「导入案例到桌面供缓存复算」**，再手动选择 **朝霞/晚霞** 点击查询。程序会自动勾选原桌面「从案例缓存读取」，并禁止此情况下向 OM 发起联网请求。若老案例缓存无法满足新版请求结构，**共享 Engine 会显示旧保存结果**，而不是伪称已经重算概率。请查看本次结果和诊断报告。

## 当前验证与限制

- 对合肥历史案例核对：0 km 原生高云 100%，旧 OM 高云 13.913%，当前有效云量回归 100%；17 个距离点中有 9 个超过 25 pp 的分层冲突。这里的统计是离线**输入复核**，不等于旧案例的概率/光路结论已经重新计算。
- GFS 原生 9 点范围云量与 OM 25km 格点 proxy 的时间批次、空间尺度可能不同，因此不保证数值一致。此修复只阻止 proxy 无条件覆盖主云量。
- 旧 ZIP 案例读取时，本桌面版本不会根据旧 JSON 自动重新推导所有评分；必须通过完整请求缓存的显式重算或重新联网查询。若原有缓存缺字段，不能凭空补齐。
- 需要真实 Windy/OM 模式再次比对时，请用在线查询或已保存快照；所有离线操作本身都不触发天气 API。
- 普通原桌面启动程序仍保留供对照，不影响网页、Pro / Lite 前端或 GitHub Actions。

## 额外离线命令行诊断（无 GUI 也可）

在本文件夹命令行：

```bat
python -m desktop.gfs_om_case_audit "C:\\...\\2026年11月20日_合肥_GFS.zip" --csv om_compare.csv
```

只输出云量数据审计，不触发天气服务。
